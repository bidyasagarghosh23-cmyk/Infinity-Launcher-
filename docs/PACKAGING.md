# Windows and Android packages

The **Android and Windows packages** GitHub Actions workflow builds the native
Tauri application, checks the package formats, and publishes the results as a
GitHub prerelease. Binary packages are release assets, not files committed to
Git.

## Downloads and compatibility

| Asset | Target | Build |
|---|---|---|
| `Infinity-Launcher-1.0.0-windows-x64-setup.exe` | Windows 10/11, Intel/AMD x64 | Optimized release, NSIS installer |
| `Infinity-Launcher-1.0.0-windows-x64.exe` | Windows 10/11, Intel/AMD x64 | Optimized release, standalone executable |
| `Infinity-Launcher-1.0.0-android-preview.apk` | Android 8+, ARM64 and x86_64 | Debug-signed universal sideload preview |

The Windows packages are **unsigned** unless a signing certificate is configured
separately. Windows may show an unknown-publisher warning. WebView2 is required;
the installer can bootstrap it, while the standalone executable expects it to
be installed already. These packages are x64, not Windows ARM64.

The APK is signed with the CI Android **debug key**, so it can be installed for
testing without a production signing secret. It is not a Play Store release.
The debug key is not a persistent release identity: a later CI build may have a
different key and require uninstall/reinstall. Back up your data before that.
For distributable, upgradeable Android releases, configure your own protected
release keystore using the Tauri Android signing instructions.

**Android gameplay limitation:** this APK is an instance/download manager. It
does not include an Android-compatible JVM, native rendering bridge or touch
controls for Minecraft: Java Edition. The app explains this and disables Java
game launch actions. Use the Windows package to play. The APK does not turn Java
Edition into Bedrock Edition.

Microsoft sign-in also needs an owner-configured Azure application client ID
(`INFINITY_MS_CLIENT_ID`); see [AUTH.md](AUTH.md). Offline profiles do not need
that configuration, but online servers can require a legitimate account.

## Run the packaging workflow

The workflow runs on pushes to the active Arena packaging branch that change
application/build inputs. It can also be started from **Actions → Android and
Windows packages → Run workflow**. Both native builds must succeed before the
prerelease is published. Each run gets its own versioned prerelease tag.

The release includes `SHA256SUMS.txt` and `INSTALL.md`. On Windows:

```powershell
Get-FileHash .\Infinity-Launcher-1.0.0-windows-x64-setup.exe -Algorithm SHA256
```

On Linux/macOS:

```bash
sha256sum -c SHA256SUMS.txt
```

Only install packages from a source you trust. A valid APK signature proves the
signing identity, not that the app is safe or has passed device testing.

## Build Windows locally

Use a Windows x64 machine with Node.js 22, stable Rust (MSVC toolchain), and
Visual Studio C++ Build Tools:

```powershell
npm ci
npm test
npm run tauri build -- --target x86_64-pc-windows-msvc --bundles nsis
```

The standalone executable is under `src-tauri/target/release/` or the explicit
target's `release/` directory. The installer is under the corresponding
`target/.../release/bundle/nsis/` directory.

## Build Android locally

Prerequisites:

- Node.js 22 and stable Rust.
- JDK 21 (the CI toolchain; the Gradle version generated by this Tauri CLI must
  support it).
- Android SDK command-line tools and an installed NDK. CI uses
  `29.0.14206865`. Set `ANDROID_HOME` and `NDK_HOME`.
- Let Gradle install the SDK platform/build tools required by the generated
  project after accepting the Android SDK licenses.

```bash
npm ci
rustup target add aarch64-linux-android x86_64-linux-android
npm run tauri android init -- --ci --skip-targets-install
npm run tauri android build -- --ci --apk --debug --target aarch64 x86_64
```

The generated project lives under `src-tauri/gen/android/` and is intentionally
ignored by Git. The APK is under
`src-tauri/gen/android/app/build/outputs/apk/universal/debug/`.

For a production Android release, use your own signing configuration and a
release build instead of copying the CI debug-signing approach. Keep keystores
and passwords out of Git.

## Validation scope

CI runs TypeScript checks, the headless UI smoke test (including the Android
launch guard), native compilation, Windows PE checks, APK signature verification
with `apksigner`, APK metadata inspection, ZIP integrity checks and SHA-256
checksums. It does **not** claim a real-device gameplay test, Microsoft account
end-to-end test, antivirus clearance or production code signing.
